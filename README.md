# YASB Native Portable — source-builder kit r1

**Mode: NATIVE ONLY.** This repository is an **independent builder**, not an upstream fork and not the compiled YASB app itself. Its workflow downloads a published stable YASB source release, verifies the exact Git SHA, patches source-level storage and local Komorebi discovery, compiles the actual Python/PyQt6 application into Windows PE EXEs with cx_Freeze, checks its native ZIP, then invokes the pinned Universal Release Publisher. No PortableApps launcher or installer is used.

**Honesty:** the kit's offline tests run in development. Hosted Windows compilation, interactive GUI functionality, real socket/subscription handling, appbar geometry, and storage-trace containment remain **NOT YET VERIFIED** until the workflow and desktop acceptance tests are run. Changes to newer upstream source are refused when an expected source anchor disappears; they are not silently guessed.

## 1. Quick setup (GitHub Desktop, no local compiler)

1. At GitHub, choose **New repository**. Name it `YASB-Native-Portable-Builder` (or any distinct name). Do **not** fork `amnweb/yasb`.
2. Choose **Private** if you don't want built release artifacts accessible to the public. A public repository's release ZIPs are public. You can use GitHub's hosted Windows runner on an eligible plan, subject to GitHub's usage limits.
3. In GitHub Desktop, choose **File > Clone repository** and clone the empty repository. An empty remote repository can be cloned; if Desktop offers **Create a repository** instead, follow its instructions to create the matching local directory and publish it to the new remote.
4. Extract **the contents** of this builder-kit ZIP **directly into the cloned repository folder**, not into an extra nested folder. Ensure `.github/workflows/build-native.yml` is copied. In File Explorer, enable **View > Show > Hidden items** if necessary.
5. In GitHub Desktop, select **Commit to main**, then **Push origin**. There is no manual Git initialization, developer fork, Python installation, PowerShell policy change, or local compiler required.
6. On GitHub, open the repository's **Actions** tab. If prompted, enable workflows. Select **Build YASB Native Portable (source built)**, click **Run workflow**, leave `upstream_version=latest`, `css_engine_sha=auto`, `package_revision=r1`, and `publish_release=true`.
7. Read the logs. A red step means build validation or publishing failed. A green workflow means headless CI steps passed, **not** that the Windows desktop behaved correctly.
8. Under **Releases**, download the `YASB-NativePortable-v...-x64-r...zip` plus the publisher-generated `SHA256SUMS.txt`. Compare SHA-256 checksums with `Get-FileHash` or Windows `certutil`.
9. Extract the application ZIP to a writeable directory such as `D:\Portable\YASB-NativePortable`. Double-click **`yasb.exe` directly**. Keep `lib`, `assets`, `Data` and all adjacent runtime files together. On first run, YASB's setup wizard may initialize config.
10. **Upgrade:** exit through the tray or `yasbc.exe stop`, back up the whole directory, replace application binaries/resources and `README.txt`, **never overwrite or delete `Data`**. If an old release has a different data schema, restore the whole backup rather than mixing versions.

## 2. Application ZIP layout (generated by Windows Actions)

```
YASB-NativePortable/
    yasb.exe                  DIRECT application (not a wrapper)
    yasbc.exe                 upstream CLI with native safety changes
    yasb_themes.exe           upstream theme application
    yasb_cloud.exe            upstream optional Cloud application
    lib/                      bundled Python, PyQt6 and other DLLs
    assets/                   upstream icons/resources
    Data/
        Config/               config.yaml, styles.css, .env, logs
        State/                YASB cache/state; cloud encrypted credentials
    LICENSES/                upstream MIT + installed dependency notices
    DEPENDENCIES-PINNED.txt
    UPSTREAM-PATCHES.json
    SOURCE-STATIC-AUDIT.json
    SOURCE-IDENTITY.json
    FILE-SHA256.json
    README.txt
```

`Data/Config` and `Data/State` are present as **empty folders even before first launch**. The builder never retrieves a user's original profile. If you already have installed YASB settings, copy **only files you explicitly select** into the portable `Data/Config` after backup; never remove the installed profile. Configs containing absolute drive or user paths may need edits after relocation.

## 3. Komorebi SOCK integration

The native YASB build performs a **read-only probe** of `%LOCALAPPDATA%\komorebi\komorebi.sock` (or `YASB_KOMOREBI_SOCK_PATH`). On Windows it finds a running `komorebi.exe` by inspecting Windows process metadata and uses a sibling `komorebic.exe` in the **same running Komorebi folder**. This supports an independently portable Komorebi binary that is not registered on `PATH`. Its fallback is a valid explicitly configured CLI path, then normal `PATH`.

YASB continues to use **its actual upstream named-pipe listener** for `komorebic subscribe`. SOCK discovery is **not** a replacement for subscription and is **not proof** that workspaces or appbar offsets render correctly. No Komorebi setting is automatically edited.

If your Komorebi has nonstandard locations, create `Data\Config\.env` after the first launch:

```dotenv
YASB_KOMOREBIC_PATH=D:\Portable Apps\Komorebi\komorebic.exe
YASB_KOMOREBI_SOCK_PATH=C:\Users\USER\AppData\Local\komorebi\komorebi.sock
```

Replace those two **illustrative** paths with the actual ones. The SOCK path is usually per-current Windows user, not inside Komorebi's portable folder. Komorebi itself must be running before workspaces can populate. The YASB client periodically attempts reconnection.

**Window tiling and work-area reservation:** enable YASB's actual `window_flags: windows_app_bar` setting for Windows appbar behavior **only if tested with your monitors**, or use the Komorebi work-area offset mechanism if that is what your Komorebi config expects. Avoid enabling **both** forms of work-area reservation simultaneously without checking for double gaps. Test tiled windows, maximum window state, multiple screens, DPI changes, Explorer restart, monitor unplug/replug, and full-screen windows. The builder intentionally does not overwrite Komorebi's own config or set guessed offsets.

## 4. Native CLI and optional autostart

The application needs **no manager**: double-click `yasb.exe` directly. In the same folder, `yasbc.exe start`, `yasbc.exe stop`, `yasbc.exe reload`, `yasbc.exe log`, `yasbc.exe config-dir` and `yasbc.exe enable-autostart`/`disable-autostart` use the native build's communication identity.

- **Autostart is OFF by default.** `yasbc.exe enable-autostart` creates one opt-in **HKCU Run** entry named `YASB Native Portable`, with a quoted absolute EXE path. The operation refuses an existing same-name entry instead of overwriting it. `disable-autostart` removes it only if its value exactly matches the current folder's path.
- Before relocating the folder, run `yasbc.exe disable-autostart`, then move, then opt back in. If you already moved it, check the original entry in `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` and **only after checking its ownership** repair/delete it manually. The CLI deliberately will not delete an entry belonging to another location.
- For safety, the inherited `--force` process-name kill, installed MSI `update` and `set-channel`, destructive `reset`, global task-based autostart and machine-wide crash-dump commands are blocked. Cloud automatic backup can create an **explicitly opted-in** separate scheduled task; the main YASB app does not create one automatically.
- Portable/native and installed YASB use **distinct mutex, CLI pipe, log pipe, Windows app identity, and startup value names**. Do not assume running two visible status bars on the same monitor will look good; coexistence safety and visual compatibility are different problems.

## 5. Build details and source identity

- Release discovery: published stable numeric semver tags from GitHub Releases only; excludes drafts/alpha/beta/RC/preview/nightly. An explicit stable version may be supplied. Unverified branch `main` is never a fallback.
- Upstream code: `git clone` of the exact tag followed by a check that its commit matches GitHub API's peeled Git-tag SHA. The download uses TLS. No local compiler or upstream fork is required.
- Dependencies: the upstream exact Python requirements plus pinned `cx-freeze==8.6.4`. The upstream `qt-css-engine` dependency points to mutable `dev`, so the workflow resolves its commit SHA and patches the Python dependency to that immutable reference before pip installs it. It records `pip freeze --all`, source-patch original/patched hashes, upstream commit, builder commit and release identity.
- Compiling: `python src/build.py build` from `src/` via `cx_Freeze` builds real `yasb.exe`, `yasbc.exe`, `yasb_themes.exe` and `yasb_cloud.exe`. The upstream MSI tooling is **not run**, preventing its installer-only HKLM/Start Menu/URL-protocol registrations.
- Packaging: checks PE format, x64 machine fields, cx_Freeze `lib/library.zip`, assets, all four EXEs, empty Data directories, forbidden PortableApps metadata, file hashes and ZIP CRC, then prints the real ZIP's SHA-256.
- Publishing: only `vhick/portable-release-publisher@v1.1.1`, with dry-run first, explicit tag prefix and GITHUB_TOKEN. The shared Package Builder / `custom-nsis` / `official` engines are **not applicable** to native mode.
- Builds on different days can have different bytes because tools/metadata/dependencies and timestamps are not completely locked. This is a **traceable/provenance-recorded build**, not a demonstrated bit-for-bit reproducible build or signed release.

## 6. Safety, rollback and known limits

Portable storage is implemented **in upstream source** at its actual config/LocalAppData/Cloud helper functions. No wrapper, `%APPDATA%` global override, post-exit harvesting, TraceGuard, registry cleanup, or PortableApps metadata exists. Normal Windows components may still create caches, UserAssist/Recent history, GPU shader caches, firewall settings (if applicable), notification entries, search history, and clipboard history. User-added/third-party widgets can create their own host state. A static source scan is included but is **not a runtime guarantee**.

Cloud account sessions and encryption keys use **Windows DPAPI**; they are stored under `Data/State/cloud` but might not decrypt on a different Windows user/machine. Never weaken Windows credential protection to gain portability. Reauthentication may be necessary after moving computers.

**No automatic binary self-updater:** install new verified ZIPs yourself while the app is completely shut down. Before upgrading, back up `Data` and binaries. Restore entire backup on failure. Retain both versions if a config schema change makes rollback incompatible. Do not force-terminate installed YASB to upgrade portable YASB.

**Licenses:** YASB is MIT, Qt CSS Engine is MIT, Qt/PyQt has additional third-party license obligations. The kit gathers installed Python dependency metadata/license files and includes YASB's upstream license. This inventory is helpful evidence, but must be audited against actual bundled binaries before public redistribution. No claim is made that it exhaustively satisfies Qt/PyQt or all transitive binary notices.

**Code signing:** this is an unofficial, unsigned build. Do not claim official YASB, PortableApps.com or Microsoft certification. Windows Defender/SmartScreen may warn on unsigned binaries; do not disable security software or use AV-evasion methods.

For detailed source audit, tests, troubleshooting and limitations see `docs/`.
